# Implementing Passkey Authentication with Cometh Connect 4337 SDK and NextAuth.js

## 1. Introduction

### 1.a. Goal: Integrating Cometh Connect Passkeys with NextAuth.js via Direct SDK Calls

This guide provides a comprehensive, step-by-step implementation plan for integrating Cometh Connect's passkey-based smart contract wallets with NextAuth.js authentication within a Next.js application. The primary objective is to enable a seamless, secure, and passwordless user authentication experience leveraging WebAuthn technology and ERC-4337 Account Abstraction principles. This document focuses specifically on utilizing direct calls to the Cometh Connect 4337 SDK functions `createSafeSmartAccount` and `retrieveAccountAddressFromPasskey`, combined with NextAuth.js's `CredentialsProvider` and JWT session strategy. The aim is to deliver a modern, non-custodial authentication flow that enhances both user experience and security.

### 1.b. Core Technologies Overview

This implementation relies on a synergy of modern Web3 and web authentication technologies:

* **Cometh Connect 4337 SDK (`@cometh/connect-sdk-4337`)**: This is the central Software Development Kit (SDK) for interacting with Cometh's infrastructure for passkey management and ERC-4337 smart wallet operations. It provides the necessary functions (`createSafeSmartAccount`, `retrieveAccountAddressFromPasskey`, `SmartAccountClient` interaction) to manage user wallets controlled by passkeys. The SDK leverages `viem` internally for blockchain interactions. It's important to use this specific package, as it represents Cometh's current approach aligned with ERC-4337 and modern tooling.
* **Passkeys (WebAuthn)**: This W3C standard enables passwordless authentication using public-key cryptography. Instead of passwords, users authenticate via device-bound credentials (like fingerprint, face ID, or PIN) managed securely by the operating system or browser. Cometh Connect abstracts the direct WebAuthn API interactions, simplifying passkey creation and usage for wallet control.
* **ERC-4337 (Account Abstraction)**: This Ethereum standard allows users to use smart contracts as their primary accounts, moving beyond the limitations of Externally Owned Accounts (EOAs). It introduces concepts like UserOperations (pseudo-transactions), Bundlers (nodes that package UserOps), and Paymasters (contracts that can sponsor gas fees), enabling features like gasless transactions, social recovery, and batch operations.
* **EIP-1271 / EIP-6492**: These Ethereum Improvement Proposals define standards for verifying signatures generated by smart contracts. EIP-1271 provides a general mechanism (`isValidSignature`), while EIP-6492 extends this to support verification for smart contracts that have not yet been deployed to the blockchain. This is crucial because smart contracts, unlike EOAs, do not possess private keys in the traditional sense; their signature validation logic is defined within the contract code itself. EIP-6492 is particularly relevant for flows where a wallet address is predicted before its first transaction deploys it.
* **NextAuth.js**: A popular authentication library for Next.js applications. This guide utilizes specific components:
   * `CredentialsProvider`: This provider allows for custom authentication logic, making it suitable for integrating non-standard flows like passkey signature verification.
   * `JWT Strategy`: Configured via `session: { strategy: 'jwt' }`. This approach stores session information within a secure, encrypted JSON Web Token (JWT). **NextAuth stores this JWT in a secure, HttpOnly browser cookie, not in localStorage.**
   * `Database Adapter` (Implicit): While using a JWT strategy for sessions, a database (like PostgreSQL or MySQL via Prisma) is still essential in this implementation to store persistent user data, specifically the `walletAddress`, the authentication nonce, and its expiry.
* **viem**: A modern, lightweight, and type-safe TypeScript interface for interacting with Ethereum. It is used by the Cometh Connect 4337 SDK and will be used directly in the backend for verifying EIP-1271/6492 signatures via standard JSON-RPC calls.

### 1.c. Benefits

This integration offers several advantages:

* **Passwordless Authentication**: Eliminates the need for users to create, remember, or manage passwords.
* **Enhanced Security**: Utilizes non-custodial smart contract wallets where users retain control. Passkeys offer strong protection against phishing. Secure HttpOnly cookies protect session tokens.
* **Improved User Experience (UX)**: Streamlines onboarding. Users can create or access wallets using familiar device authentication methods. Potential for gas sponsoring via ERC-4337 paymasters further reduces friction.
* **Smart Wallet Features**: Leverages ERC-4337 capabilities like transaction batching and gas abstraction.

### 1.d. Cometh API Scope vs. Standard RPC Calls

It is essential to understand the distinction:

* **Cometh Connect APIs**: Specialized backend services and SDK functions for Account Abstraction infrastructure (Bundler, Paymaster, Wallet Prediction/Recovery/Management via `createSafeSmartAccount`, `retrieveAccountAddressFromPasskey`).
* **Standard Ethereum JSON-RPC Calls**: Fundamental blockchain interactions (reading data, verifying signatures) performed against a node provider (e.g., Alchemy, Infura) using tools like `viem`. Crucial for:
   * **Signature Verification (EIP-1271/6492)**: Verifying the `signedNonce` requires calling `isValidSignature` on the smart contract wallet (or simulating it via EIP-6492). This is done using `viem`'s `publicClient.verifyMessage`, making underlying `eth_call` requests to the `RPC_URL`. **This is not a Cometh-specific API call. Cometh's API is NOT used for signature verification.**
   * Fetching Balances/Transaction History: Uses standard RPC calls.

Cometh Connect provides the specialized infrastructure for passkey-controlled smart wallets and AA features, but verifying signatures and reading general blockchain state relies on standard RPC communication facilitated by `viem`.

3. Backend Implementation (NextAuth & Nonce API)
3.a. Nonce API Endpoint (/api/auth/nonce)
Purpose: Generate a unique, secure nonce (challenge), associate it with the walletAddress, set an expiry, store it, and return it to the frontend. This prevents replay attacks.
Implementation:
// src/app/api/auth/nonce/route.ts
import { NextResponse } from 'next/server';
import { PrismaClient } from '@prisma/client';
import { isAddress } from 'viem';
import crypto from 'crypto';

const prisma = new PrismaClient();
const NONCE_EXPIRY_MINUTES = 5; // Set nonce validity period

export async function POST(request: Request) {
 try {
   const { walletAddress } = await request.json();

   if (!walletAddress || !isAddress(walletAddress)) {
     return NextResponse.json(
       { message: 'Invalid or missing wallet address' },
       { status: 400 }
     );
   }

   // 1. Generate Secure Nonce
   const nonce = crypto.randomBytes(32).toString('hex');

   // 2. Calculate Expiry Time
   const nonceExpiry = new Date(Date.now() + NONCE_EXPIRY_MINUTES * 60 * 1000);

   // 3. Store Nonce and Expiry in DB
   // Use upsert: Creates user if not exists (associating address), or updates existing user's nonce.
   // Handles first-time interaction before full registration in the unified flow.
   // For stricter security, you might only update here and create user explicitly in authorize.
   await prisma.user.upsert({
     where: { walletAddress: walletAddress },
     update: {
       nonce: nonce,
       nonceExpiry: nonceExpiry,
     },
     create: {
       walletAddress: walletAddress,
       nonce: nonce,
       nonceExpiry: nonceExpiry,
       isActive: true, // Set defaults
     },
   });

   // 4. Return Nonce to Frontend
   return NextResponse.json({ nonce });

 } catch (error) {
   console.error('Nonce generation error:', error);
   return NextResponse.json(
     { message: 'Internal Server Error' },
     { status: 500 }
   );
 } finally {
   await prisma.$disconnect();
 }
}

Security Considerations:
* Secure Generation: Use crypto.randomBytes.
* Short Expiry: Keep NONCE_EXPIRY_MINUTES low (1-5 mins).
* Secure Storage: Store server-side in DB, linked to walletAddress.
* Single Use: Invalidate immediately after successful use (in authorize function).
* Rate Limiting: Implement rate limiting on this endpoint.
3.b. NextAuth Configuration (/api/auth/[...nextauth]/route.ts)
Purpose: Configure NextAuth.js with CredentialsProvider for the custom passkey flow, JWT session management, and backend signature verification using viem. This is where the core backend authentication logic resides after the frontend calls signIn.
Implementation:
// src/app/api/auth/[...nextauth]/route.ts
import NextAuth, { NextAuthOptions, User as NextAuthUser } from 'next-auth';
import CredentialsProvider from 'next-auth/providers/credentials';
import { PrismaClient } from '@prisma/client';
import { createPublicClient, http, isAddress, verifyMessage, Hex } from 'viem';
import { mainnet, polygon, arbitrumSepolia } from 'viem/chains'; // Import desired chains

const prisma = new PrismaClient();

// Configure your Viem Public Client
// Ensure RPC_URL and the chain match your project setup
const publicClient = createPublicClient({
 chain: arbitrumSepolia, // Example: Use the chain your app targets
 transport: http(process.env.RPC_URL),
});

// Define custom user type for authorize return and JWT/Session callbacks
interface CustomUser extends NextAuthUser {
 id: string; // Database User ID
 walletAddress: string;
}

export const authOptions: NextAuthOptions = {
 providers: [
   CredentialsProvider({
     name: 'Cometh Passkey',
     credentials: {
       walletAddress: { label: "Wallet Address", type: "text" },
       signedNonce: { label: "Signed Nonce", type: "text" },
       challenge: { label: "Nonce Challenge", type: "text" },
     },
     // This 'authorize' function executes on the backend when signIn('cometh-credentials', ...) is called
     async authorize(credentials): Promise<CustomUser | null> {
       // --- Step 1: Receive Credentials ---
       if (!credentials?.walletAddress || !credentials.signedNonce || !credentials.challenge) {
         console.error('Missing credentials for authorization');
         throw new Error('Missing credentials');
       }
       const { walletAddress, signedNonce, challenge } = credentials;
       if (!isAddress(walletAddress)) {
         console.error('Invalid wallet address format:', walletAddress);
         throw new Error('Invalid wallet address format');
       }

       try {
         // --- Step 2: Retrieve User and Stored Nonce from DB ---
         const user = await prisma.user.findUnique({
           where: { walletAddress: walletAddress },
         });
         if (!user) {
           console.error('User not found for address:', walletAddress);
           throw new Error('User not found. Please register first.'); // Or handle implicit registration if desired
         }
         if (!user.nonce || !user.nonceExpiry) {
           console.error('Nonce or expiry missing for user:', walletAddress);
           throw new Error('Authentication challenge not found or expired. Please try again.');
         }

         // --- Step 3: Validate Nonce Content and Expiry ---
         if (user.nonce !== challenge) {
           console.error('Nonce mismatch for user:', walletAddress);
           throw new Error('Invalid authentication challenge.');
         }
         if (new Date() > user.nonceExpiry) {
            console.error('Nonce expired for user:', walletAddress);
            // Clear expired nonce for security
            await prisma.user.update({
               where: { id: user.id },
               data: { nonce: null, nonceExpiry: null },
            });
           throw new Error('Authentication challenge expired. Please try again.');
         }

         // --- Step 4: Verify Signature (EIP-1271 / EIP-6492) ---
         // This is the CRITICAL security check. It uses viem and an RPC node.
         // Cometh's API is NOT involved here.
         console.log(`Verifying signature for address ${walletAddress} with challenge ${challenge}`);
         const isValidSignature = await publicClient.verifyMessage({
           address: walletAddress as `0x${string}`,
           message: challenge, // The original nonce is the message that was signed
           signature: signedNonce as Hex,
         });

         if (!isValidSignature) {
           console.error('Signature verification failed for user:', walletAddress);
           throw new Error('Signature verification failed.');
         }
         console.log('Signature verification successful for user:', walletAddress);

         // --- Step 5: Update DB - Invalidate Nonce ---
         // Nonce is cleared immediately after successful use to prevent replay.
         // User record already exists (found in Step 2).
         await prisma.user.update({
           where: { id: user.id },
           data: { nonce: null, nonceExpiry: null },
         });

         // Optional: Check User Status (e.g., isActive flag)
         if (!user.isActive) {
            console.warn('Attempted login by inactive user:', walletAddress);
            throw new Error('Account is disabled.');
         }

         // --- Step 6: Return User Object ---
         // Returning a user object signals successful authorization to NextAuth.
         console.log('Authorization successful for user:', user.id, user.walletAddress);
         return {
           id: user.id,
           walletAddress: user.walletAddress,
           // Include other properties needed in JWT/session if available on user model
           // email: user.email,
           // name: user.name,
         };

       } catch (error: any) {
         console.error('Authorization error:', error);
         // Re-throw the specific error message for frontend display via signIn response
         throw new Error(error.message || 'Authentication failed');
       } finally {
         // Optional: Disconnect Prisma client in serverless environments if not handled globally
         // await prisma.$disconnect();
       }
     }
   })
 ],
 session: {
   strategy: 'jwt', // Force JWT strategy
   maxAge: 30 * 24 * 60 * 60, // 30 days session expiry
 },
 callbacks: {
   // jwt callback: Called AFTER authorize succeeds. Populates the JWT.
   async jwt({ token, user }) {
     if (user) { // 'user' is the object returned from 'authorize'
       const customUser = user as CustomUser;
       token.userId = customUser.id;
       token.walletAddress = customUser.walletAddress;
     }
     return token;
   },
   // session callback: Called AFTER jwt callback. Populates the client-side session object.
   async session({ session, token }) { // 'token' is the output of the 'jwt' callback
     if (token && session.user) {
       (session.user as any).id = token.userId;
       (session.user as any).walletAddress = token.walletAddress;
     }
     return session;
   },
 },
 pages: {
   signIn: '/', // Redirect users to homepage for the unified button flow
   error: '/auth/error', // Optional: Custom error page
 },
 secret: process.env.NEXTAUTH_SECRET, // Required for JWT encryption
 debug: process.env.NODE_ENV === 'development', // Enable debug logs in development
};

// --- Step 7: Create Session (Handled by NextAuth) ---
// If authorize returns a user object, NextAuth automatically:
// 1. Calls the 'jwt' callback to create the JWT payload.
// 2. Encrypts the JWT.
// 3. Sets the encrypted JWT in a secure, HttpOnly cookie.
// 4. Calls the 'session' callback to prepare the client-side session object.

const handler = NextAuth(authOptions);

export { handler as GET, handler as POST };

Key Aspects & Flow Summary:
1. Frontend signIn Call: Initiates the process, sending credentials to the backend.
2. Backend authorize Execution:
   * Receives credentials.
   * Looks up user/nonce in DB.
   * Validates nonce content & expiry.
   * Crucially verifies signature via viem.verifyMessage (EIP-1271/6492 using RPC node).
   * Clears the used nonce from DB upon success.
   * Returns user object { id, walletAddress, ... } on success.
3. Backend NextAuth Session Creation: If authorize succeeds:
   * jwt callback populates the token.
   * NextAuth creates encrypted JWT and sets HttpOnly cookie.
   * session callback prepares client session object.
4. Backend -> Frontend Result: The success ({ ok: true, error: null, ... }) or error ({ ok: false, error: '...', ... }) result is sent back to the frontend signIn promise.

  if (!response.ok) {
    const errorData = await response.json();
    throw new Error(errorData.message || `Nonce API request failed: ${response.status}`);
  }
  const data = await response.json();
  if (!data.nonce) throw new Error('Nonce not received from API');
  return data.nonce;
}

async function signNonce(client: any, nonce: string): Promise<Hex> { // Replace 'any' with SDK type
 // ... implementation ...
  if (!client?.account?.signMessage) {
       throw new Error('SmartAccountClient is invalid or signMessage is unavailable.');
  }
  try {
      const signature = await client.account.signMessage({ message: nonce });
      return signature as Hex;
  } catch (error: any) {
      console.error('Signing error:', error);
      throw new Error(`Failed to sign message: ${error.message || 'Unknown error'}`);
  }
}

// --- Step 8: Return Result (Handled by this function's caller) ---
// This function initiates the backend flow and returns the result promise.
async function callNextAuthSignIn(walletAddress: string, signedNonce: Hex, challenge: string): Promise<any> { // Replace 'any' with actual signIn response type
 // ... implementation ...
  const signInResponse = await signIn('cometh-credentials', {
    walletAddress: walletAddress,
    signedNonce: signedNonce,
    challenge: challenge,
    redirect: false,
  });

  // The caller of this function will handle the resolved promise (signInResponse)
  // which contains the success/error status from the backend authorize flow.
  if (!signInResponse?.ok) {
    console.error('Sign-in failed:', signInResponse?.error);
    // Throwing error here propagates it to the main handler's catch block
    throw new Error(signInResponse?.error || 'Authentication failed');
  }
  console.log('Sign-in successful via NextAuth!');
  return signInResponse; // Return response for potential further handling
}

5. Security Considerations
Implementing authentication requires careful attention to security:
      * (a) Nonce Security: Fundamental to prevent replay attacks.
      * Server-Side Generation: Use crypto.randomBytes.
      * Short Expiry: 1-5 minutes validity.
      * Single-Use: Invalidate immediately after successful use in authorize.
      * Secure Storage: Store in DB, coupled to walletAddress.
      * (b) Mandatory Backend Signature Verification: Non-negotiable. Verify signedNonce in the authorize function using viem's publicClient.verifyMessage against the RPC_URL. This correctly handles EIP-1271/6492. Never trust client-side verification.
      * (c) API Key Security:
      * NEXT_PUBLIC_COMETH_API_KEY: Required client-side for this direct-call flow. Mitigate risk by using keys with least privilege and configuring allowed origins in the Cometh dashboard.
      * Server-Side Secrets: NEXTAUTH_SECRET, DATABASE_URL, and any Cometh secret keys must remain strictly server-side.
      * (d) CSRF Protection: Handled automatically by NextAuth.js for its API routes when using the signIn client function.
      * (e) Input Validation: Rigorously validate all inputs on the backend (/api/auth/nonce, authorize function). Check types, formats (isAddress), and presence of required fields.
      * (f) Passkey/WebAuthn Security Benefits: Leverage inherent phishing resistance, no shared secrets, and hardware-backed key storage.
      * (g) Rate Limiting: Implement strict rate limiting on /api/auth/nonce and the implicit NextAuth callback endpoint (/api/auth/callback/cometh-credentials) to prevent brute-force/DoS attacks.
      * (h) JWT Expiry Handling: NextAuth.js handles JWT expiry automatically. useSession will return status: 'unauthenticated', requiring the user to re-authenticate via the button, triggering a fresh nonce/signature flow.
      * (i) JWT Storage: NextAuth.js stores session JWTs in secure, HttpOnly cookies by default when using the JWT strategy. This prevents access from client-side JavaScript, mitigating XSS risks related to token theft.
