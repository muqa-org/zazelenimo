Implementing Passkey Authentication with Cometh Connect 4337 SDK and NextAuth.js
1. Introduction
Purpose
This report provides an expert technical guide for implementing a secure and user-friendly authentication system leveraging passkeys via the Cometh Connect 4337 SDK, integrated within a Next.js application using the NextAuth.js framework. The goal is to detail a robust flow that combines the ease of passwordless login with the security and capabilities of non-custodial, smart contract-based wallets.
Context
The Web3 ecosystem is rapidly evolving, moving beyond traditional Externally Owned Accounts (EOAs) towards more sophisticated solutions like Account Abstraction (AA). This shift addresses the inherent limitations of EOAs, particularly concerning user experience (UX) and security. Users often struggle with seed phrases and gas fees, creating significant barriers to adoption. Simultaneously, Web2 applications have embraced passwordless authentication methods like passkeys (WebAuthn), offering enhanced security and convenience. The challenge lies in bridging these two worlds: implementing familiar, seamless Web2 login experiences while harnessing the power and security of Web3's non-custodial smart contract wallets.
Solution Overview
This report outlines a solution that integrates several key technologies:
1. Cometh Connect 4337 SDK: A specialized Software Development Kit designed to create and manage ERC-4337 compliant smart contract wallets controlled by passkeys.1 It simplifies interaction with WebAuthn and account abstraction protocols.
2. NextAuth.js: A comprehensive authentication library for Next.js applications, providing the framework for managing user sessions and integrating custom authentication logic.4
3. Passkeys (WebAuthn): The W3C standard enabling passwordless, phishing-resistant authentication using public-key cryptography managed securely by the user's device.
4. ERC-4337: The Ethereum standard defining account abstraction without requiring consensus-layer changes, enabling smart contract wallets with features like gas sponsorship and custom validation logic.
5. viem: A modern, lightweight TypeScript interface for Ethereum, used both by the Cometh SDK and crucially for backend signature verification.3
Value Proposition
Implementing this integrated solution offers significant advantages:
* Passwordless Login: Eliminates the need for users to manage passwords, enhancing convenience and security.
* Enhanced Security: Leverages the phishing resistance of passkeys and the non-custodial nature of smart contract wallets, where private keys remain within the user's secure hardware enclave.3
* Improved User Experience: Streamlines onboarding and login. Furthermore, the underlying ERC-4337 infrastructure opens possibilities for gasless transactions through integrated paymasters 9, further reducing friction.
* Smart Contract Wallet Features: Users benefit from the inherent capabilities of smart contract wallets, such as potential social recovery mechanisms 10 and programmable security policies.
2. Core Concepts Overview
A thorough understanding of the underlying technologies is essential for successful implementation.
Cometh Connect 4337 SDK
The Cometh Connect 4337 SDK serves as the central component for interacting with passkey-controlled smart contract wallets within the application. It abstracts the complexities involved in both WebAuthn interactions and ERC-4337 operations. Developers interact with high-level functions provided by the SDK, which internally handle the necessary cryptographic operations and blockchain communications.1
Key functions relevant to this authentication flow include:
* createSafeSmartAccount: Used during new user registration. It triggers the browser's WebAuthn API for passkey creation and predicts the associated smart contract wallet address (typically a Gnosis Safe 11) without immediately deploying it.1
* retrieveAccountAddressFromPasskey: Used during existing user login. It prompts the user to authenticate with an existing passkey and retrieves the corresponding wallet address.12
* SmartAccountClient: An object initialized after successful wallet creation or connection. It provides methods like signMessage to perform signing operations using the user's passkey via the underlying smart wallet's mechanisms.1
The SDK is built upon modern libraries like viem, leveraging its capabilities for blockchain interaction.3 The abstraction provided by the SDK is significant; developers do not need to manually construct WebAuthn API calls or format ERC-4337 UserOperations. Instead, they utilize functions like createSafeSmartAccount and signMessage, allowing focus to remain on the application's core logic rather than the intricacies of passkey cryptography or account abstraction protocols.
NextAuth.js
NextAuth.js acts as the authentication backbone for the Next.js application, managing session state and orchestrating the login/logout flows. For this specific implementation, several NextAuth.js components are critical:
* CredentialsProvider: This provider is essential because the passkey/wallet signature verification process is a custom flow, unlike standard OAuth protocols.14 It allows developers to define custom authentication logic within its authorize function.4
* authorize Function: This asynchronous function within the CredentialsProvider configuration is the heart of the backend authentication logic. It receives the credentials sent from the frontend (wallet address, signed nonce, original nonce) and performs all necessary validation steps, including nonce checks and signature verification [4-S_S34, S_R51, S_R56, S_R108, S_R118, S_R142, S_R150, S_R161, S_R172].
* JWT Strategy: Configured via session: { strategy: 'jwt' }, this tells NextAuth.js to manage sessions using JSON Web Tokens. The JWT is stored in a secure, HttpOnly browser cookie, containing encrypted session information.
* jwt and session Callbacks: These callback functions allow customization of the JWT payload and the session object exposed to the client-side, respectively. The jwt callback is used to encode necessary user details (like user ID and wallet address) into the token after successful authorization. The session callback then selectively exposes parts of this token data to the frontend useSession hook or getSession calls.
* Database Adapter (e.g., @next-auth/prisma-adapter): While CredentialsProvider documentation often discourages database persistence with JWTs, this specific authentication flow requires linking the verified walletAddress to a persistent user record in the database. This association is fundamental to identifying the user across sessions. Therefore, database interaction (finding or creating a user based on walletAddress) is essential within the authorize function's logic, even when using the JWT session strategy. This represents a nuanced but necessary application of the CredentialsProvider.
Passkeys (WebAuthn)
Passkeys are based on the WebAuthn W3C standard, providing a secure and user-friendly method for passwordless authentication. They utilize public-key cryptography, where a unique key pair is generated for each website or application. The private key is stored securely within the user's device hardware (like a Secure Enclave or TPM) or a password manager, and never leaves it. Authentication involves the user proving possession of the private key by signing a challenge, typically confirmed via biometrics (fingerprint, face scan) or a device PIN.8
The Cometh Connect SDK seamlessly integrates with the browser's native WebAuthn API. When functions like createSafeSmartAccount or signMessage are called, the SDK triggers the appropriate browser prompts for passkey creation or usage, abstracting the direct API calls from the developer.2 This approach offers strong phishing resistance, as passkeys are bound to specific domains, and enhances security by keeping the private key confined to the user's secure environment.3
ERC-4337 Smart Accounts (e.g., Gnosis Safe)
ERC-4337 introduces account abstraction to Ethereum, allowing smart contracts to act as primary user accounts. Unlike EOAs, which are controlled solely by a private key, smart accounts are controlled by their code. This enables features like multi-signature logic, social recovery, spending limits, and, crucially for this flow, custom signature validation schemes.
Cometh Connect utilizes Gnosis Safe contracts (or compatible implementations) as the underlying smart wallet.11 A key feature employed is "lazy deployment".2 When a new user registers, createSafeSmartAccount predicts the deterministic address where the Safe contract will be deployed, but the actual deployment transaction only occurs when the user initiates their first on-chain action (e.g., sending a transaction). This saves upfront gas costs for user onboarding.
EIP-1271 & EIP-6492
These Ethereum Improvement Proposals are critical for verifying signatures originating from smart contract wallets:
* EIP-1271 (Standard Signature Validation Method for Contracts): Defines a standard interface (isValidSignature) that smart contracts can implement to declare how signatures should be validated against them.17 When the backend needs to verify if a signature allegedly from a smart contract address is valid, it calls this function on the contract. This is essential because the smart contract itself (based on its internal logic, e.g., checking against authorized passkey signers) determines validity, not a simple cryptographic check like ecrecover used for EOAs.
* EIP-6492 (Signature Validation for Predeploy Contracts): Addresses the challenge posed by lazy deployment. Since the Cometh wallet address exists before the contract is deployed, a direct EIP-1271 call would fail. EIP-6492 specifies a signature format wrapper that includes the necessary information (like the contract's creation code) to allow verification even before the contract exists on-chain.17
The combination of Cometh's lazy deployment 2 and the need for the smart contract to validate passkey signatures makes robust EIP-1271/EIP-6492 verification on the backend indispensable. Standard EOA verification methods are insufficient. Libraries like viem simplify this by automatically handling both EIP-1271 and EIP-6492 when verifying messages against potential contract addresses.6
viem
viem is a modern, highly efficient TypeScript library for interacting with Ethereum. It is utilized internally by the Cometh Connect 4337 SDK.3 Its relevance in this authentication flow extends to the backend, specifically for signature verification. The publicClient.verifyMessage function provided by viem is the recommended tool for validating the signedNonce within the NextAuth authorize function.6 This function intelligently checks if the address belongs to an EOA or a contract and performs the appropriate verification, including handling EIP-1271 calls and EIP-6492 checks for undeployed contracts.

```
4.4 Backend: API & NextAuth Configuration
This section details the backend logic required for nonce management and authentication verification.
               1. (Step 3) Nonce Generation API Endpoint (/api/auth/nonce): Create a Next.js API route (e.g., pages/api/auth/nonce.ts) to handle nonce generation and storage.
TypeScript
// pages/api/auth/nonce.ts
import type { NextApiRequest, NextApiResponse } from 'next';
import { PrismaClient } from '@prisma/client';
import crypto from 'crypto';

const prisma = new PrismaClient();

export default async function handler(req: NextApiRequest, res: NextApiResponse) {
 if (req.method!== 'GET') {
   res.setHeader('Allow',);
   return res.status(405).end(`Method ${req.method} Not Allowed`);
 }

 const { walletAddress } = req.query;

 if (!walletAddress |

| typeof walletAddress!== 'string' ||!/^0x[a-fA-F0-9]{40}$/.test(walletAddress)) {
return res.status(400).json({ message: 'Valid walletAddress query parameter is required' });
}






  try {
   // Optional: Check if user exists before generating nonce for login attempts
   // const existingUser = await prisma.user.findUnique({ where: { walletAddress } });
   // if (!existingUser) {
   //   // For login, maybe return 404? For registration, maybe proceed? Depends on flow.
   //   // return res.status(404).json({ message: 'User not found for nonce generation' });
   // }

   const nonce = crypto.randomBytes(32).toString('hex');
   const expires = new Date(Date.now() + 5 * 60 * 1000); // 5 minute expiry

   // Use upsert: find user by walletAddress, update nonce/expiry if found,
   // OR create user if not found (adjust based on whether registration is implicit here)
   // IMPORTANT: For security, consider only *updating* existing users here,
   // and handle user creation *only* within the authorize callback after successful verification.
   // This example uses upsert for simplicity but might need refinement.
   await prisma.user.upsert({
     where: { walletAddress: walletAddress },
     update: {
       nonce: nonce,
       nonceExpiry: expires,
     },
     create: {
       walletAddress: walletAddress,
       nonce: nonce,
       nonceExpiry: expires,
       // Add other default fields if creating here (e.g., email if available)
     },
   });

   return res.status(200).json({ nonce });
 } catch (error) {
   console.error('Nonce generation error:', error);
   return res.status(500).json({ message: 'Internal server error' });
 } finally {
   await prisma.$disconnect();
 }
}
```
This endpoint generates a secure nonce, sets an expiry, and stores it in the database record associated with the provided `walletAddress`. Storing the nonce server-side linked to the specific user and with a short expiry is crucial to prevent replay attacks. An attacker cannot simply reuse a captured signature because the corresponding nonce on the server will either be different, expired, or already cleared after a successful login.

The authorize function serves as the critical security checkpoint. It meticulously validates the incoming credentials against server-side state (user record, nonce, expiry) and performs the essential EIP-1271/6492 signature verification via viem. Only if all checks pass is a user object returned, signaling NextAuth.js to proceed with session creation. The jwt and session callbacks then ensure that necessary identifiers like userId and walletAddress are securely embedded in the session token and made accessible to the application.
4.5 NextAuth Session Management (Automatic)
Once the authorize function successfully returns a user object, NextAuth.js handles the subsequent session management automatically based on the configuration:
                     1. JWT Generation: A JSON Web Token (JWT) is created. The jwt callback allows for the inclusion of specific user data (like id, walletAddress) within this token's payload.
                     2. Cookie Storage: This JWT is encrypted (using NEXTAUTH_SECRET) and stored in a secure, HttpOnly browser cookie.29 This cookie cannot be accessed directly by client-side JavaScript, enhancing security.
                     3. Session Verification: On subsequent requests to the server (API routes or server-rendered pages), the browser automatically sends the session cookie. NextAuth.js middleware or helper functions (getServerSession, auth) can decrypt and validate the JWT from the cookie to determine the user's session status and retrieve the stored payload.
                     4. Client-Side Access: The session callback filters and shapes the data from the token that is made available to the client-side useSession hook or getSession function. This ensures sensitive parts of the token (if any) are not unnecessarily exposed to the browser.
5. Security Considerations
Implementing authentication, especially involving cryptographic keys and blockchain interactions, requires careful attention to security:
                     * Nonce Security: Nonces are fundamental to preventing replay attacks. They must be generated server-side using a cryptographically secure random number generator. They must be stored securely (e.g., in the database associated with the user's walletAddress), have a short expiry time (e.g., 5 minutes), and be invalidated (cleared from the database) immediately after successful use.
                     * Backend Signature Verification: This is the most critical security step. Never trust signature verification performed on the client-side. The backend authorize function must independently verify the signedNonce against the challenge (nonce) and walletAddress using viem's publicClient.verifyMessage. This function correctly handles EIP-1271 and EIP-6492, ensuring the signature is valid according to the smart contract's logic, whether deployed or not.
                     * API Key Security: The COMETH_API_KEY is used client-side to initialize the SDK.2 While necessary, be aware of its exposure. If Cometh provides an API_SECRET for backend operations (like paymaster configuration 9 or recovery 25), ensure it is never exposed client-side and is stored securely as an environment variable on the server.
                     * CSRF Protection: NextAuth.js provides built-in CSRF protection using the double submit cookie method. Ensure this is enabled and correctly configured, especially if using custom sign-in pages.28 The signIn client function typically handles CSRF tokens automatically.30
                     * Input Validation: Rigorously validate and sanitize all inputs received by the backend API endpoints (/api/auth/nonce, /api/auth/[...nextauth].ts), including walletAddress, challenge, and signedNonce, to prevent injection attacks or unexpected behavior.
                     * Passkey Security: The security of the user's private key relies on the underlying WebAuthn protocol and the security of the user's device (secure enclave, OS security) or password manager. The application itself does not handle the private key directly.8
                     * Rate Limiting: Implement rate limiting on the /api/auth/nonce and /api/auth/callback/cometh-credentials (handled by NextAuth) endpoints to mitigate brute-force attacks or denial-of-service attempts.
6. Troubleshooting & Common Pitfalls
                     * SmartAccountClient Initialization for Login: The most common error for existing users is incorrectly initializing the SmartAccountClient. Remember to call createSafeSmartAccount with the smartAccountAddress option after retrieving the address via retrieveAccountAddressFromPasskey.2 Calling it without the address attempts to create a new passkey.
                     * EIP-1271/6492 Verification Errors: If publicClient.verifyMessage fails:
                     * Ensure the backend publicClient is connected to the correct RPC endpoint for the target chain.
                     * Verify the smart contract wallet (if deployed) correctly implements the EIP-1271 isValidSignature function according to the Cometh Safe specifications.
                     * Confirm the viem version being used supports EIP-6492 for verifying signatures against undeployed contracts.6
                     * Check for correct parameter types (Address, Hex) being passed to verifyMessage.
                     * Nonce Issues:
                     * Mismatch: Ensure the challenge sent to signIn exactly matches the nonce fetched from the backend and stored in the database.
                     * Expiry: Verify the nonceExpiry logic is correct and the server/client clocks are reasonably synchronized. Increase expiry slightly if network latency is an issue, but keep it short.
                     * Replay: Ensure the nonce is reliably cleared from the database immediately after successful validation in the authorize function.
                     * WebAuthn Errors: These can originate from the browser or OS.
                     * Check browser compatibility with WebAuthn.
                     * Users might cancel the prompt.
                     * Device security policies might interfere (e.g., no biometric sensor available).
                     * The Cometh SDK might provide specific error codes or fallbacks (e.g., local wallet fallback, though potentially disabled 2). Check SDK documentation for error handling specifics.
                     * NextAuth Configuration Errors:
                     * Ensure the CredentialsProvider id ('cometh-credentials') matches the first argument in the signIn call.
                     * Check jwt and session callback logic if expected user data (ID, walletAddress) isn't available client-side. Ensure data is correctly added to token and then forwarded to session.user.
                     * Be mindful of JWT size limits; avoid storing excessive data in the token.
                     * CORS Issues: If your frontend and backend API routes are served from different origins (domains/ports), configure CORS headers appropriately on your Next.js backend API routes.
7. Conclusion
Summary
This report has detailed a comprehensive process for integrating Cometh Connect's passkey-based smart contract wallets with NextAuth.js for secure and user-friendly authentication. The flow leverages createSafeSmartAccount for new user registration and passkey creation, retrieveAccountAddressFromPasskey for existing user login, and SmartAccountClient.signMessage for challenge signing via WebAuthn. The backend, powered by NextAuth.js's CredentialsProvider, uses a secure nonce mechanism and viem's publicClient.verifyMessage to perform robust EIP-1271/EIP-6492 signature verification against the user's smart wallet address. Session management is handled via JWTs stored in secure cookies.
Benefits Revisited
The outlined implementation successfully bridges Web2 convenience with Web3 capabilities. Users benefit from a passwordless, phishing-resistant login experience using familiar device biometrics or PINs. Security is enhanced through non-custodial key management within secure enclaves and robust server-side verification. The use of ERC-4337 smart accounts provides a foundation for advanced features like gas abstraction and social recovery, ultimately improving the overall user onboarding and interaction experience for decentralized applications.
